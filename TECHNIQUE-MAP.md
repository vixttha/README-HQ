# README technique map

This map groups individual techniques by the job they do for a reader or maintainer. Linked techniques have a catalog record. Plain entries describe candidates for later research and may need stronger evidence before they get a record.

A technique belongs wherever its behavior helps. This map gives each one a primary home for browsing. The searchable catalog can list a single record under more than one task.

## Purpose and audience

Help readers decide whether they’re in the right place.

- [State the project’s purpose](techniques/project-purpose-statement.md) — Tell a new reader what the project does and what they can accomplish with it.
- **Audience and use cases** — Name the people and jobs the project serves.
- **Value proposition** — Explain the practical payoff or problem the project removes.
- **Project status and maturity** — Distinguish a preview, stable release, or archived project.
- **Explain how to choose an update channel** — When multiple release streams are offered, state the differences in stability, update cadence, and what the reader should install. nginx labels mainline, stable, and legacy downloads. [nginx release channels](https://nginx.org/en/download.html)
- **Distinguish source from the shipped product** — Explain what readers are browsing, which product or distribution it produces, and where each set of terms applies. VS Code does this for Code - OSS and Microsoft’s Visual Studio Code distribution. [VS Code source and distribution](https://github.com/microsoft/vscode/blob/f26893c248aa2b2ef1f3dba2134d9d1806559186/README.md#L9-L15)
- **Match model variants to their files and runtime** — List the exact variants readers can obtain and show how the base or instruction-tuned version, weight format, and precision affect runtime compatibility and resource needs. Point to the matching model card and example for each supported option. For derived weights, link the base model and name the relationship. [Gemma variant and memory guide](https://gemma.ai/models/gemma-4/) · [Gemma GGUF model card](https://huggingface.co/google/gemma-3-12b-pt-qat-q4_0-gguf)
- **Capabilities at a glance** — Show the few important things readers can do today.
- **Scope boundaries** — Call out material limitations or environments outside the supported scope.
- **State what the dataset represents** — Describe the unit of observation, collection period, geographic or population coverage, and material exclusions. Name the release the coverage applies to and distinguish sampled records from the population they represent by labeling each explicitly. [U.S. Census ACS microdata coverage](https://api.census.gov/data/2024/acs/acs5/pums.html) · [W3C DCAT coverage properties](https://www.w3.org/TR/vocab-dcat-3/)
- **List what each format can read, write, and preserve** — Separate input and output support. State which content or formatting a named conversion may lose, and how to check a result that needs fidelity. Pandoc distinguishes its readers and writers and explains lossy conversions. [Pandoc conversion guidance](https://pandoc.org/MANUAL.html#description)
- **Disclose telemetry defaults and controls** — Name the data a tool collects, the default participation state, and how to view or change the setting. Next.js documents the data collected and its opt-out control. [Next.js telemetry documentation](https://nextjs.org/telemetry)
- **Alternatives and tradeoffs** — Explain when a related tool or approach fits a reader better.
- **Roadmap pointer** — Link planned work to a maintained roadmap and distinguish it from available features.
- **Status badges** — Surface meaningful build, release, or license signals and link each badge to its source.

[GitHub README guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) · [Pinned BART introduction](https://github.com/vixttha/Blender-Agent-Refinement-Toolkit/blob/3e7f9e02e61739825b56bcafecebbd0221cc9657/README.md)

## Demos and visuals

Show what using the project looks like.

- **Live demo or playground** — Link directly to a usable experience and state access requirements. [itch.io’s browser game publishing guide](https://itch.io/docs/creators/html5)
- **Link both a notebook preview and a runnable notebook** — Label the link for inspecting saved results and the link for launching the notebook at the corresponding revision. GitHub renders notebooks statically, while Binder can open a particular notebook for execution. [GitHub notebook rendering](https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files#working-with-jupyter-notebook-files-on-github) · [Binder notebook links](https://mybinder.readthedocs.io/en/latest/howto/user_interface.html)
- **Screenshot or result preview** — Show the key product screen or output readers should recognize.
- **Annotated screenshot** — Identify the controls or evidence a reader needs to notice.
- **Animated micro-demo** — Show a short interaction sequence that needs no narration.
- **Captioned video walkthrough** — Demonstrate a longer workflow with captions or a transcript. [Google accessible media guidance](https://developers.google.com/style/accessibility)
- **Minimal working example** — Show the smallest realistic input and operation that demonstrate the capability. [Godot’s platformer demo](https://github.com/godotengine/godot-demo-projects/blob/b761b4cd5718a7118f2c95eb55f181d0a5f004f1/2d/platformer/README.md#L23-L32)
- **Architecture or flow diagram** — Show component relationships or the order of steps.
- **Asset caption and provenance** — Name what a visual shows and identify its source or build where relevant.
- **Show how asset variants map to published files** — Give the file naming pattern, label the dimensions or styles that change the filename, and show where to check whether a combination exists. Fluent UI’s SVG README specifies the names and which file inventory determines availability. [Fluent UI SVG naming and availability](https://github.com/microsoft/fluentui-system-icons/blob/6c2c9075cf8952ef48369b2475233b6e9761efed/packages/svg-icons/README.md#L99-L110) [Google’s Material Icons guide](https://developers.google.com/fonts/docs/material_icons)
- [Write image alternatives for their purpose](techniques/purpose-specific-image-alternatives.md) — Give informative, decorative, functional, and complex visuals the text treatment their roles require.
- **Theme-aware images** — Check readability against light and dark backgrounds and provide variants when needed.
- **Text equivalent for a chart or diagram** — Put essential values, conclusions, or relationships in surrounding text.

[GitHub diagram support](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams) · [W3C WAI image guidance](https://www.w3.org/WAI/tutorials/images/) · [Pinned AlderVale visual example](https://github.com/vixttha/AlderVale-Pact-of-Ten/blob/a6c2060b8175f505cc6327ccb5658cc00a458b24/README.md)

## Quickstart and adoption

Get a reader to a first meaningful action.

- **One prominent first action** — Lead with a recognizable task such as play, try, install, or adopt.
- **Provide a starter control map** — List the actions a player needs in the first minute and map them to each supported input type. Point to remapping settings where they exist. [Years to Spare control table](https://github.com/r6mez/Years-to-Spare/blob/55dc4527b475efa3c030a7c42ecf265bddf3d0c8/README.md#L83-L95) · [Game Accessibility Guidelines on remapping](https://gameaccessibilityguidelines.com/allow-controls-to-be-remapped-reconfigured/)
- **Prerequisites next to the task** — Name tools, versions, access, and prior setup before any commands depend on them.
- **Show the permissions automation needs** — Name the caller permissions the example needs and what each one allows. For reusable workflows, state where those permissions must be granted. [actions/checkout recommended permissions](https://github.com/actions/checkout/blob/f548e57e544e1ff5a4c46bf1e1b8685f8e4a348a/README.md#L377-L384) · [GitHub nested workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#access-and-permissions-for-nested-workflows)
- **Link a parts list for the hardware revision** — Give builders a bill of materials that matches the design they are assembling. Include part identifiers, quantities, and any documented substitutions, with a way to map each item to the design. [OSHWA documentation checklist](https://certification.oshwa.org/process/documentation.html)
- **Match firmware to the physical hardware revision** — Help readers identify the device revision and map it to the correct build or download target. QMK distinguishes buildable keyboard revisions and documents target selection. [QMK keyboard guidelines](https://docs.qmk.fm/hardware_keyboard_guidelines) · [QMK target selection](https://docs.qmk.fm/getting_started_make_guide)
- **Set a time and cost expectation before setup** — State how long the example usually takes and whether it can create billable resources, with a link to current terms when pricing depends on an account or provider. AWS examples show [an estimated duration](https://docs.aws.amazon.com/hands-on/latest/setup-environment/setup-environment.html) and [a cost label](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/tutorial-launch-my-first-ec2-instance.html).
- [Write a copyable Quickstart](techniques/copyable-quickstart.md) — Give readers ordered commands they can paste into the supported shell.
- **Separate platform commands** — Label POSIX and PowerShell paths where their commands differ.
- **Installation methods** — Distinguish packages, installers, source builds, and other supported options.
- **Show how to enable optional capabilities** — Identify what the base install enables and which feature flag or package extra enables each optional capability. Put optional setup beside the example that requires it. Tokio documents the default and the features readers can select. [Tokio feature flags](https://docs.rs/tokio/latest/tokio/#feature-flags) · [Python dependency extras](https://packaging.python.org/en/latest/specifications/dependency-specifiers/#extras) [npm’s optional dependency behavior](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#optionaldependencies)
- **Pair the install name with the name used in code** — When distribution, import, or executable names differ, show the exact names together so readers can connect the installation step to the first use. The Python Packaging User Guide illustrates this with the Pillow distribution and its PIL import. [Python packaging names](https://packaging.python.org/en/latest/discussions/distribution-package-vs-import-package/)
- **Identify required assets distributed separately** — State which graphics, sound, models, or other runtime assets the checkout needs. Link their maintained source and say which installation routes fetch them automatically. [OpenTTD’s base assets](https://github.com/OpenTTD/OpenTTD/blob/e8a7f94481f0a545715b221c8ae63271b60df98b/README.md#L64-L84)
- **Explain how to obtain restricted inputs** — Give each restricted input an authorized acquisition route and name the eligibility, training, agreement, or approved environment that applies. Identify affected steps and the role or provider that handles access requests. [Social Science Data Editors README template](https://github.com/social-science-data-editors/template_README/blob/development/template-README.md) · [UK Data Service controlled access](https://ukdataservice.ac.uk/find-data/access-conditions/secure-application-requirements/)
- **Describe what the installer changes** — Tell readers where binaries or files are installed, which persistent user settings change, and what supported option controls those changes. uv documents its installation directory and shell-profile behavior. [uv installer options](https://docs.astral.sh/uv/reference/installer/)
- **Label ownership of installation channels** — Identify who maintains and supports each package or installer so readers know where to report installation problems. GitHub CLI links community-supported routes separately. [GitHub CLI installation links](https://github.com/cli/cli/blob/f24a94ffcb8c344ed5db0e4fb9a4d1fffd42c256/README.md#L33-L58) · [Linux package maintainers](https://github.com/cli/cli/blob/f24a94ffcb8c344ed5db0e4fb9a4d1fffd42c256/docs/install_linux.md#L186-L222)
- **Starting directory and checkout** — State where commands begin and which revision or project root they expect.
- **List the local service URLs by purpose** — When setup starts several services, tell readers which address opens the app, dashboard, API, or other local tool. Supabase CLI labels the addresses it prints for its development stack. [Supabase local development output](https://supabase.com/docs/guides/local-development/cli/getting-started) [Docker’s container development walkthrough](https://docs.docker.com/guides/lab-container-supported-development/)
- **Safe configuration example** — Use labeled placeholders and explain where values belong.
- **Give service examples a sandbox route** — Name the sandbox or mock used by the example and state what effects it simulates. Label the difference from live operation so readers know where the example can be run. [Stripe testing environments](https://docs.stripe.com/testing-use-cases) · [Stripe Sandboxes](https://docs.stripe.com/sandboxes)
- **Offer an importable API request collection** — Link a reusable request collection so readers can run the same requests in their API client. Identify the target environment and show which values they need to supply locally. [Postman’s README integration](https://learning.postman.com/docs/publishing-your-api/run-in-postman/creating-run-button/)
- **Show configuration precedence** — Explain which setting wins when flags, environment variables, configuration files, and defaults disagree. Give one concrete conflict example in the supporting reference. Terraform documents the order for root module input variables. [Terraform variable precedence](https://developer.hashicorp.com/terraform/language/values/variables#variable-definition-precedence)
- **Sample fixture or starter input** — Provide a small known input that readers can use immediately.
- **Provide a shareable substitute for restricted data** — Offer a documented, structurally compatible sample when real inputs cannot be distributed. Tell readers which checks the sample supports and which findings require the authorized inputs. Keep the sample path clearly labeled in the run instructions. [World Bank synthetic-data verification guidance](https://github.com/worldbank/wb-reproducible-research-repository/blob/main/guidance_note_wb.md#packages-with-restricted-or-confidential-data)
- **Guest or offline first run** — Offer a first-use path with minimal account or network dependencies when supported.
- **Show how to prepare an offline install** — Separate gathering dependencies on a connected machine from installing the staged set on the offline target. State which platform and runtime the bundle must match. pip documents both stages. [pip download](https://pip.pypa.io/en/stable/cli/pip_download/) · [Installing from local packages](https://pip.pypa.io/en/stable/user_guide/#installing-from-local-packages)
- **Offer an isolated trial command** — Give the reader a short way to try a tool without installing it into their project. State what runner is required and what can be cached. uv demonstrates a temporary tool environment with `uvx`. [uv README example](https://github.com/astral-sh/uv/blob/c99faeeeeb8318d874007b4c48635d009838c1a0/README.md#L147-L166) · [Environment and cache behavior](https://github.com/astral-sh/uv/blob/c99faeeeeb8318d874007b4c48635d009838c1a0/docs/concepts/tools.md#L10-L38)
- **Link directly to a project-configured workspace** — Point readers to a preconfigured development workspace tied to the repository and intended branch. State what account or local tooling it needs. GitHub Codespaces and VS Code Dev Containers document repository links for this. [Codespaces deep links](https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/setting-up-your-repository/facilitating-quick-creation-and-resumption-of-codespaces) · [VS Code Dev Containers](https://code.visualstudio.com/docs/devcontainers/create-dev-container)
- **Prerequisite or installation check** — Show a fast way to check that the local environment is ready before the demo.
- **Copy-in or template adoption path** — Identify what to copy, where it goes, and how to check the resulting project.
- **Upgrade or migration route** — Name the starting version, intended destination, and relevant migration guide.
- **Show the order for upgrading multiple components** — When components evolve independently, show the upgrade sequence and which version combinations can coexist during the transition. Kubernetes documents both the skew limits and the supported component order. [Kubernetes version skew and upgrade order](https://kubernetes.io/releases/version-skew-policy/)
- **Give readers an upgrade preflight** — Link a compatibility check readers can run before an upgrade changes their existing installation. Explain which findings block the upgrade and where to resolve them. PostgreSQL documents a check-only path for pg_upgrade. [PostgreSQL upgrade compatibility check](https://www.postgresql.org/docs/current/pgupgrade.html)
- **Cleanup or reset instructions** — Show how a reader can leave a temporary demo or restore a clean starting point.
- **Explain what uninstall removes and retains** — State which commands or files uninstall removes and what happens to data, configuration, caches, or installed components. Point to the data-preservation path when it matters. Docker Desktop distinguishes uninstall effects from backup and restore. [Docker Desktop uninstall effects](https://docs.docker.com/desktop/uninstall/) · [Docker Desktop backup and restore](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/)
- **Preview changes before applying them** — When a workflow changes state and offers a preview, give the preview and apply steps distinct labels. Explain which changes the preview can predict. Terraform documents its plan separately from apply. [Terraform plan](https://developer.hashicorp.com/terraform/cli/commands/plan) · [Ansible check mode limits](https://docs.ansible.com/projects/ansible/latest/playbooks_checkmode.html) [Helm upgrade preview options](https://helm.sh/docs/helm/helm_upgrade/)

[Google code-sample guidance](https://developers.google.com/style/code-samples) · [Pinned BART Quickstart](https://github.com/vixttha/Blender-Agent-Refinement-Toolkit/blob/3e7f9e02e61739825b56bcafecebbd0221cc9657/README.md) · [Pinned template adoption guide](https://github.com/vixttha/Brand-Identity-Template/blob/87d0f9aedbe69ca4b16815d6b3329efcf5889da9/README.md)

## First result and recovery

Help the reader recognize success and get unstuck.

- [Show a recognizable first result](techniques/first-success-milestone.md) — Tell the reader what success looks like immediately after the first real task.
- **Expected output contract** — Separate stable result fields from variable example values when exact comparison matters.
- **Give a readiness check before the first request** — After the startup command, show what indicates the dependency can accept traffic and how the reader can check it. A service may be running before its dependencies are ready. [Docker Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/) · [Kubernetes readiness probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)
- **Document the scripting interface** — Show where scripts can find structured output and which outcomes return which exit codes. Include command-specific exceptions when they affect automation. GitHub CLI documents both formatting and exit behavior. [GitHub CLI output formatting](https://cli.github.com/manual/gh_help_formatting) · [Exit codes](https://cli.github.com/manual/gh_help_exit-codes) · [Authentication status exception](https://cli.github.com/manual/gh_auth_status)
- **Show how to retrieve every page of results** — Give an example that spans multiple pages, follows the continuation link or cursor, and states when to stop. GitHub’s REST guide demonstrates following the next-page link until it is absent. [GitHub REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)
- **Save or persistence checkpoint** — Tell readers what should survive a restart and how to confirm it.
- **Map application files by purpose** — List the locations for user data, configuration, runtime state, and cache on supported platforms. Identify overrides and distinguish files a reader needs to preserve from data the application can rebuild. [Syncthing configuration and database locations](https://docs.syncthing.net/users/config.html) · [XDG data and cache conventions](https://specifications.freedesktop.org/basedir/)
- **State which saved data a release can open** — Name which older saves, archives, or project files the new version can read, and describe rollback separately where supported. OpenTTD documents loading saves from older revisions. [OpenTTD save compatibility](https://github.com/OpenTTD/OpenTTD/blob/e8a7f94481f0a545715b221c8ae63271b60df98b/README.md#L56-L62)
- **Show a restore check against a separate destination** — Pair a backup path with a small restore exercise into a separate destination and show what to inspect in the restored copy. The restic restore guide explains selecting the snapshot and destination. [restic restore guide](https://restic.readthedocs.io/en/stable/050_restore.html) · [Borg restore quickstart](https://borgbackup.readthedocs.io/en/master/quickstart.html)
- **First successful result link** — Point to the file, page, or artifact the task created so it is easy to inspect.
- **Next action after success** — Offer a natural second task once the first one works.
- **Put a practice task before its worked solution** — When the README is also a learning guide, give readers a short task and a way to check their attempt. Put the worked answer behind a labeled section or link. The Carpentries uses separate challenge and solution blocks. [The Carpentries exercise format](https://carpentries.github.io/lesson-development-training/instructor/lesson-content.html#adding-exercises)
- **Recovery beside the failed step** — Put a common failure and its recovery close to the command or action that produces it.
- **Explain what happens when a step is repeated** — State whether repeating a command converges on the same result, resumes work, or creates another copy. Ansible’s module guide describes idempotency as a behavior that module authors should provide. Check the actual commands before promising it. [Ansible module behavior](https://docs.ansible.com/projects/ansible/latest/module_plugin_guide/modules_intro.html)
- **Document what happens with concurrent writers** — Say which shared state is protected, when writers wait or fail, and whether the behavior depends on the storage backend or deployment mode. Terraform scopes locking to supported backends. SQLite distinguishes concurrent readers from writers in WAL mode. [Terraform state locking](https://developer.hashicorp.com/terraform/language/state/locking) · [SQLite WAL concurrency](https://sqlite.org/wal.html#concurrency)
- **Document automatic retry boundaries** — Tell automated readers which responses allow another attempt, which server signal controls the delay, and when retries should stop. GitHub’s REST guidance distinguishes waiting according to response headers from persisting after repeated failures. [GitHub REST retry guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately)
- **Diagnostic decision guide** — Route different symptoms to the relevant fix instead of listing generic troubleshooting.
- **Separate diagnostic capture from sharing** — Tell readers how to capture relevant evidence, where the resulting bundle lands, and how to inspect or anonymize it before sending it through the support route. Docker distinguishes diagnostic capture and upload. Atlassian documents support-bundle anonymization. [Docker Desktop diagnostics](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/) · [Atlassian support-bundle guidance](https://support.atlassian.com/jira/kb/anonymize-jira-support-zip-data/)
- **Show how to activate an installed extension** — Name the first command, view, or event that activates the extension and the behavior a reader should see. VS Code distinguishes installing an extension from activating it on a matching event. [VS Code extension anatomy](https://code.visualstudio.com/api/get-started/extension-anatomy) · [Activation events](https://code.visualstudio.com/api/references/activation-events)
- **Known limitations and workarounds** — State a known constraint and the currently supported path around it.
- **Explain defaults that change what readers see** — Name the input the tool omits or transforms by default, what a reader may miss, and how to change the behavior. ripgrep puts its default exclusions near its opening description. [ripgrep default search scope](https://github.com/BurntSushi/ripgrep/blob/16f9b2e64a42c43a469f72260226a6c65a4c88b9/README.md#L1-L9)

[Pinned Veraphify result example](https://github.com/vixttha/Veraphify/blob/88d5d08cd8c80de3927858685878e51b6d7c69b8/README.md) · [README HQ registry](https://github.com/vixttha/README-HQ/blob/8d50caec2bc6fcb998994a1fd302294a029325f9/techniques/registry.json)

## Navigation and accessibility

Get readers to the right information with minimal scanning.

- [Route by reader task](techniques/role-based-entry-points.md) — Give distinct reader goals clear routes from the same homepage.
- [Relative navigation](techniques/relative-navigation.md) — Link same-checkout guides and assets with paths relative to the Markdown file.
- **Descriptive link labels** — Use text that tells the reader where the link goes or what it does.
- **Clear heading hierarchy** — Organize sections in a predictable structure for visual scanning and assistive navigation. [Google heading structure guidance](https://developers.google.com/style/headings)
- **Table of contents or jump links** — Expose major sections when the page is long enough to need them.
- **Section deep links** — Send the reader to the relevant part of a guide and recheck anchors when headings change.
- **Send readers to docs for their installed version** — Label stable and development docs links so readers can match them to the version they are using. A branch README can link multiple editions if its audience spans supported releases. [Read the Docs version routing](https://docs.readthedocs.com/platform/stable/versions.html) · [Godot’s development docs notice](https://docs.godotengine.org/en/latest/getting_started/step_by_step/index.html)
- **Progressive disclosure** — Collapse optional details or move them to a clearly labeled supporting document. [GitHub collapsed sections](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections)
- **Use labeled callouts at the point of action** — Use short labeled notices for important context or consequences beside the relevant step. Keep essential information readable in plain text when the renderer handles callouts differently. [GitHub alerts](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts) · [Google’s notice guidance](https://developers.google.com/style/notices)
- **Give color-coded information a text label** — Label states, branches, or series in words when color conveys their meaning. Readers should still understand a status table or diagram with the colors removed. [W3C guidance on use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- **Separate guide types** — Route readers to a tutorial, how-to, reference, or explanation according to their task.
- **Give each public package its own README entry point** — Put a short orientation in the package directory so someone entering through a deep link can find its purpose, setup, and supporting docs. Google’s README guide calls this out for package directories. [Google’s package README guidance](https://github.com/google/styleguide/blob/8bdadbb0732b387aaa26f553dd9033484d1a2071/docguide/READMEs.md#L30-L55)
- **Concise comparison table** — Present repeated choices in a table when readers need to compare the same attributes.
- **Language routing** — Link translated docs and make the expected language clear.
- **Track the source revision of translations** — Link a translated README to its original and record which revision or release it follows. This lets maintainers identify what needs updating and readers find the source text when needed. Kubernetes documents its upstream-first translation workflow. [Kubernetes localization workflow](https://kubernetes.io/docs/contribute/localization/)
- **Task-local help link** — Put the relevant support path beside a high-friction step.
- **Consistent terms** — Use the same names for actions and objects as the code, UI, and linked instructions.

[GitHub README and section links](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) · [W3C accessible writing](https://www.w3.org/WAI/tips/writing/) · [Diátaxis documentation types](https://diataxis.fr/start-here/)

## Verification and trust

Make public claims traceable and scoped.

- [Execute the documented walkthrough](techniques/exact-revision-walkthrough.md) — Replay the reader’s published steps at the named revision and verify the result.
- **Turn examples into regression tests** — Generate test cases from examples in the maintained documentation source so changing an example also changes what gets tested. jq’s docs README describes the process and its Makefile connects manual examples to the test suite. [jq docs README](https://github.com/jqlang/jq/blob/5c001b18d7237cce1fdba63608732163f978dd23/docs/README.md#L1-L22) · [jq test-generation rule](https://github.com/jqlang/jq/blob/5c001b18d7237cce1fdba63608732163f978dd23/Makefile.am#L154-L170) [Python doctest documentation](https://docs.python.org/3/library/doctest.html)
- [Permanent proof links](techniques/permanent-proof-links.md) — Keep verification traceable with a commit-pinned receipt and recorded run, attempt, artifact ID, and digest.
- [Label the scope of compatibility evidence](techniques/claim-scope-labels.md) — State the version, platform, capability, and checks that support a compatibility claim. [Kubernetes client and server compatibility example](https://github.com/kubernetes-client/python/blob/92f5111c5b27dcc3004314552165d5da2190d73e/README.md#L112-L151)
- **Declared versus observed checks** — Show which checks were required and which actually ran, passed, failed, or were skipped.
- **Map each claim to the check that can reproduce it** — Pair the claim or reported result with its command, expected outcome, and the data it produces. Label claims that fall outside the reproduction instructions. [SPIN reproduction guidance](https://spin-web.github.io/SPIN2026/artifacts) · [USENIX artifact appendix guidance](https://www.usenix.org/conference/usenixsecurity22/artifact-appendix-guidelines)
- **State how close a rerun must get** — Define the acceptance threshold for numerical or stochastic outputs. Specify the metric, comparison rule, and tolerance, and explain which exact outputs or invariants still need to match. [ACM CCS artifact evaluation](https://sigsac.org/ccs/CCS2025/call-for-artifacts/) · [Computational reproduction package guidance](https://pmc.ncbi.nlm.nih.gov/articles/PMC8059663/)
- **Published release link** — Give a direct path to the release named in the README and its release notes.
- **Artifact verification instructions** — Explain how to compare a downloaded artifact with its recorded digest.
- **Show how to verify the artifact’s producer** — Where a release provides a signed attestation, show how to verify it against the expected repository or workflow. This lets readers check build origin as well as artifact identity. [GitHub build provenance and verification](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations#verifying-artifact-attestations-with-the-github-cli)
- **Combined-commit proof** — Tie a merge-readiness claim to tests on the exact combined content.
- **Lightweight link verification** — Check that critical relative targets and anchors resolve at the claimed revision.
- **Publication-path verification** — Test links and assets from the path where the README will actually ship. The Python Packaging User Guide also runs this check against the built distribution. [PyPI rendering check](https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/)
- **Verify which README appears on the repository homepage** — When multiple eligible README files exist, check which one the host surfaces and publish the expected content there. GitHub checks `.github/`, the repository root, and `docs/` in that order. [GitHub README display order](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)
- **Rendered review at two widths** — Check the landing page on wide and narrow layouts for overflow or unreadable content.
- **Check keyboard navigation on the rendered README** — Use the keyboard on the published view to reach the primary links and any collapsible controls. Check for visible focus and an order that follows the content. W3C includes these in its preliminary accessibility checks. [W3C accessibility checking guide](https://www.w3.org/WAI/test-evaluate/preliminary/)
- **Benchmark method and scope** — Describe the workload, environment, revision, and units beside a performance result.
- **Label which benchmark results can be compared** — Group results by evaluation rules and explain what each group holds constant and what it permits entrants to change. Identify the reference baseline or quality target where it determines whether two results belong together. [MLPerf Training divisions](https://mlcommons.org/benchmarks/training/#divisions) · [MLPerf Endpoints divisions and scenarios](https://docs.mlcommons.org/endpoints-submission-docs/understand/divisions-and-scenarios/)
- **Report how much repeated measurements vary** — Accompany a headline number with the number of runs, the summary statistic, and a suitable measure of spread or uncertainty. Name what changed across runs so readers can interpret the variation. [NeurIPS reporting checklist](https://neurips.cc/public/guides/PaperChecklist) · [MLPerf Training measurement rules](https://mlcommons.org/benchmarks/training/)
- **Disclose checks for training and evaluation overlap** — State what training or tuning sources were checked for overlap with the evaluation set, how matches were handled, and which inputs were unavailable for checking. Link the underlying protocol when it affects how readers interpret reported scores. [Phi-4-mini-instruct model card](https://huggingface.co/microsoft/Phi-4-mini-instruct/blob/main/README.md)
- **Show a benchmark case that changes the takeaway** — Beside a favorable result, include a reproducible workload or flag change that reduces the advantage or changes performance. ripgrep shows performance cliffs and cases with many matches. [ripgrep performance caveats](https://github.com/BurntSushi/ripgrep/blob/16f9b2e64a42c43a469f72260226a6c65a4c88b9/README.md#L77-L114)
- **Break down evaluation results by meaningful groups** — Show comparable metrics for relevant populations, languages, or operating conditions alongside aggregate results. Identify the slices actually evaluated and provide the sample sizes or coverage limits readers need to interpret the scores. [Model Cards for Model Reporting](https://arxiv.org/abs/1810.03993) · [Google evaluation guidance](https://developers.google.com/machine-learning/crash-course/fairness/evaluating-for-bias)
- **Clean consumer adoption test** — Verify documented copy-in or install steps in a fresh consumer project.
- **Offer a smoke test and a full reproduction separately** — Use a small run to establish that setup works and a separate run to reproduce the full result. State the inputs, expected outputs, and resource needs for each. [SPIN artifact README guidance](https://spin-web.github.io/SPIN2026/artifacts) · [DistServe’s two evaluation paths](https://github.com/LLMServe/DistServe/blob/82831f1604cc6b10bebd360f6c437a07790dde9f/evaluation/docs/README-AE.md#L3-L8)
- **Provide a way to verify saved results without rerunning everything** — Link precomputed outputs or intermediate results, their integrity checks, and the scripts or inputs that produced them. State what readers can check using the saved artifacts and which claims still require a fresh run. [World Bank guidance for computationally intensive packages](https://github.com/worldbank/wb-reproducible-research-repository/blob/main/guidance_note_wb.md#computationally-intensive-packages)
- **Snapshot source identity** — Record the origin and digest of frozen README or asset bytes when exact archival identity matters.

[GitHub file permalinks](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files) · [GitHub artifact validation](https://docs.github.com/en/actions/tutorials/store-and-share-data#validating-artifacts) · [Pinned audit receipt](https://github.com/vixttha/README-HQ/blob/2f66dd6aa23928716f645cfebdce462b7574c4b3/audit/evidence/v0.0.6.67-full-stack.json) · [README HQ registry](https://github.com/vixttha/README-HQ/blob/8d50caec2bc6fcb998994a1fd302294a029325f9/techniques/registry.json)

## Handoff and maintenance

Help the next owner, contributor, or agent take responsibility for the project.

- [Link authoritative agent instructions](techniques/agent-instruction-pointer.md) — Point an agent to the repository’s applicable instructions from the README.
- **Developer entry point** — Link the source layout, setup, and shortest routine development check.
- **Contribution route** — Point to contribution rules, issue templates, and where work is reviewed. [Open Source Guides](https://opensource.guide/starting-a-project/)
- **Recognize contribution types beyond code** — Label what people contributed, such as documentation, design, translation, or testing, in the README or linked credits. The All Contributors specification describes these recognitions and a generated contributor table. [All Contributors specification](https://allcontributors.org/en/project/specification/requirements/)
- **Explain where project decisions are made** — Link a project’s governance and identify who makes major decisions. Give proposals a route when that route differs from submitting a patch. Kubernetes’s steering README describes its decision-making scope and links its charter. [Pinned Kubernetes steering README](https://github.com/kubernetes/community/blob/e1963fc0dd9debd04690163f50a6178e278b9779/committee-steering/README.md#L9-L15)
- **Support and issue route** — Tell readers where to report a bug or ask for help and what evidence to include.
- **License and reuse link** — Point to the actual terms and distinguish project assets with different terms.
- **Attribution and data provenance** — Link the source and terms for material external assets or datasets.
- **Route readers to editable designs and manufacturing exports** — Give separate links to the preferred files for modifying the design, files prepared for fabrication, and human-readable drawings where provided. Label the toolchain and revision that produced the exports. [OSHWA design-file guidance](https://oshwa.org/resources/sharing-best-practices/)
- **Include a data dictionary for shared datasets** — Explain file relationships, field names, units, and missing-value codes so another person can interpret the data. Link the full dictionary when it needs its own file. [Cornell’s research-data README guide](https://data.research.cornell.edu/data-management/sharing/readme/)
- **Show how source data becomes published files** — Trace each important derived file to its source inputs and the processing stage that produced it. Link the scripts or workflow and call out filtering, aggregation, or normalization decisions that affect reuse. [Dryad data documentation](https://datadryad.org/help/guides/best_practices) · [DVC pipeline dependencies and outputs](https://doc.dvc.org/user-guide/pipelines/defining-pipelines)
- **Explain how dataset splits were made** — Name the purpose, size, and construction rule for each partition. State which unit is kept together within a single partition, such as a speaker or account, and show readers how to select the intended split. [Samrómur speech dataset README](https://huggingface.co/datasets/language-and-voice-lab/samromur_asr) · [scikit-learn grouped splits](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupKFold.html)
- **Explain how dataset labels were assigned** — Document the annotation task and label rules. Link annotator instructions and describe how disagreement was handled or measured at the level readers will use, such as records, spans, or tokens. [RefRESD dataset README](https://huggingface.co/datasets/eleftheria/refresd/blob/33c084dafbec95b939fdd16be527d74fcefdc406/README.md) · [Hugging Face dataset card template](https://huggingface.co/datasets/templates/dataset-card-example/blob/main/README.md?code=true)
- **Explain uncertainty in published measurements** — Identify the fields or derived values affected by measurement uncertainty. Define the error or confidence quantities, their units and interpretation, and the method used to estimate them where these details affect reuse. [USGS data-quality guidance](https://www.usgs.gov/data-management/documenting-data-quality-considerations) · [NIST guidance on reporting measurement uncertainty](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-7-reporting-uncertainty)
- **Security reporting route** — Link the project’s supported private disclosure process when applicable.
- **Citation instructions** — Point researchers to the maintained citation metadata where appropriate. [Zenodo’s version-specific records and citations](https://help.zenodo.org/docs/deposit/manage-versions/)
- **Cite the exact subset of changing data** — When a result depends on a filtered subset of a changing data source, record the query or selection rules and the data version or timestamp. Link a persistent identifier for the versioned query or a frozen subset when available. [Research Data Alliance dynamic data citation recommendations](https://doi.org/10.15497/RDA00132)
- **Changelog and version navigation** — Show where release history lives and which version the reader is viewing.
- **Give a deprecation notice a replacement and timeline** — Name the affected interface, link the replacement or migration route, and distinguish the deprecation date from any planned retirement date. Link the authoritative policy when it governs multiple interfaces. [IETF Deprecation header field](https://www.rfc-editor.org/rfc/rfc9745.html) · [IETF Sunset header field](https://www.rfc-editor.org/rfc/rfc8594.html)
- **Identify the source of truth when repositories are mirrored** — Name the canonical repository and explain which revision identifiers to cite from a mirror. SQLite’s GitHub README points to Fossil and tells readers where to find the official check-in name. [SQLite mirror guidance](https://github.com/sqlite/sqlite/blob/28c1e4669d7649506c5bf640f62ce3abfc0114fa/README.md#L15-L29) [Kubernetes’s published staging repositories](https://github.com/kubernetes/kubernetes/blob/dee14a0ede00099d6441a8991ad6137b938d2a9d/staging/README.md#L1-L16)
- **Turn an archived README into a handoff** — Put the maintained successor and new project name, if any, at the top of the archive. State what remains accessible at the old location. Prisma Next explains its move and archive status before its historical README content. [Prisma Next archive handoff](https://github.com/prisma/prisma-next/blob/55458c441d2cf452028c22eed21370447720840a/README.md#L1-L10)
- **Human guide for a structured inventory** — Pair a machine-readable manifest with an explanation of its reader-facing purpose.
- **Link the machine-readable interface contract** — Point to the specification or schema for the interface addressed by the README and identify its version. Integrators can inspect operations and field requirements in the contract while following the short example in the README. [OpenAPI interface description](https://spec.openapis.org/oas/v3.2.1.html) [Microsoft’s OpenAPI generation guide](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/openapi)
- **Show how another workflow consumes an output** — Document output names and show a caller reading one of those outputs. Demonstrate the boundary between steps or jobs when it changes the syntax. [Artifact action outputs](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md#L118-L125) · [Caller examples](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md#L362-L389)
- **State what event consumers can assume about delivery** — Say whether event delivery can repeat or arrive out of order and where to find the identifier needed to recognize a repeat. Stripe’s webhook guidance documents both cases. [Stripe webhook event order and duplicates](https://docs.stripe.com/webhooks#event-ordering)
- **Generate repetitive README sections from their source** — Generate sections such as configuration inputs or outputs from their authoritative definitions. Bound generation with file markers so authored explanations stay editable. terraform-docs documents an injected section between comments. [terraform-docs output injection](https://terraform-docs.io/user-guide/configuration/output/#inject)
- **Reuse a README as the package listing** — Wire the maintained README into package metadata so package users see the same introduction in their registry. Check the description from the built package and resolve links in the target renderer. [PyPI packaging guide](https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/) · [Cargo manifest README field](https://doc.rust-lang.org/cargo/reference/manifest.html#the-readme-field)
- **Expose discovery metadata through the README** — Use host-supported metadata for fields such as dataset language, license, tags, and file layout. Hugging Face renders a dataset README as a card and uses its YAML fields for discovery and configuration. [Hugging Face dataset cards](https://huggingface.co/docs/hub/datasets-cards)
- **Independent version lines** — Name the product, README, or collection beside each version when their release lines differ.
- **Versioned section map** — Provide a path to find corresponding sections across archived READMEs.
- **Draft, archive, and publication stages** — Keep proposed text, frozen snapshots, and the published default-branch README distinguishable.
